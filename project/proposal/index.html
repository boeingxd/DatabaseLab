Project description

SIIT students lose institutional knowledge every year. What a course actually demands — the real workload, what the midterm looks like, which topics matter — lives in LINE groups, senior handoffs, and Google Drive links that rot between cohorts. Every intake rediscovers it from scratch.

SIIT Study Hub is a SIIT-gated archive of student-authored study material and structured exam intelligence, organized by course code. Rather than redistributing official exam papers (a copyright and academic-integrity problem), students submit structured descriptions of exams — format, coverage, allowed aids, self-rated difficulty — alongside notes, summaries, and cheat sheets. A working prototype of this idea already exists as a live web app (Postgres/Supabase); this proposal redesigns its database from scratch for CSS326's required MySQL + Node.js/Express stack, and uses the lessons learned from the prototype's real usage to design a cleaner schema than the first attempt had.

02

Who the users are, and what they can do

Students (verified via SIIT email)

  • Search and browse the course catalogue
  • View a course's aggregate exam stats (average difficulty, average time pressure, most-cited topics) before reading individual reports
  • Submit exam intelligence reports and study materials, with an optional file attachment
  • Upvote or downvote a submission's usefulness
  • Edit or delete their own submissions
  • Report another student's submission for review

Moderators (students with an elevated flag)

  • Everything a regular student can do
  • Review the report queue (grouped by resolved / unresolved)
  • Take down or restore reported content, with a note
  • Dismiss reports that don't warrant action

05

Database design

Entities, relationship sets, and the ER diagram. This redesign fixes two real problems found while auditing the working prototype: instructor/semester were duplicated free-text on every submission instead of a normalized entity, and votes/reports pointed at "either exam intel or materials" with no real foreign key. Both are fixed below by introducing CourseOffering and a Content supertype.

Entities list

User account
  • user_id — surrogate key
  • siit_email — institutional email, domain-verified
  • handle, real_name, program, year
  • password_hash, salt
  • is_admin — moderator flag
Course
  • course_id, code, title, program, credits
Instructor
  • instructor_id, name
CourseOffering new — normalizes duplicated text
  • offering_id, course_id (FK), instructor_id (FK), semester
Content supertype — disjoint, total
  • content_id, offering_id (FK), author_id (FK)
  • content_type — discriminator ('exam_intel' | 'materials')
  • file_path — optional attachment (PDF, image, or text), shared by both subtypes
  • credit_by_name, removed_at, removed_by (FK), removed_note, created_at
ExamIntel subtype
  • content_id — shared PK
  • exam_type, format (JSON), topics (JSON)
  • allowed_aids, duration_min, time_pressure, difficulty, advice
Materials subtype
  • content_id — shared PK
  • title, type, body_md

Why file_path moved to the supertype: the first pass put it only on Materials, but a student attaching a scanned cheat sheet to an exam-intel report is just as real a case — so the attachment belongs where both subtypes can reach it. The tradeoff: MySQL's CHECK constraints can only reference columns within their own table, so "a Materials row needs either body text or a file" can no longer be a single-table CHECK once the file lives on Content and the text lives on Materials. That validation moves into sp_submit_content instead — a concrete, honest example of a constraint that has to live in a procedure rather than the schema.

Vote new — activates an unused idea from the prototype
  • vote_id, content_id (FK), user_id (FK), value (±1), created_at
Report
  • report_id, content_id (FK), reporter_id (FK), reason, resolved, resolved_at, resolved_by (FK), created_at

Relationship sets

  • Content ISA {ExamIntel, Materials} — disjoint, total: every Content row is exactly one subtype.
  • User Authors Content (1:M)
  • User Casts Vote (1:M); Vote Targets Content (M:1) — together, User–Votes–Content is M:N with a value attribute.
  • User Files Report (1:M); Report Targets Content (M:1) — User–Reports–Content is M:N with reason/resolved attributes.
  • Course Has CourseOffering (1:M)
  • Instructor Teaches CourseOffering (1:M)
  • CourseOffering Has Content (1:M)

06

Understanding of procedures and triggers

Each one is motivated by a specific problem found in the working prototype, and mapped onto the week CSS326 teaches the matching concept (see the timeline).

Triggers

AFTER INSERT / DELETE · Vote
trg_vote_score

Maintains a denormalized helpfulness score on the parent Content row whenever a vote is cast or removed, so the course page can sort/filter without aggregating Vote on every read.

BEFORE INSERT / UPDATE · User
trg_enforce_siit_domain

Rejects any row whose siit_email doesn't match the institutional domain, at the database layer — the same rule the app layer enforces, so a bug or a second write path can't bypass it.

BEFORE UPDATE · Report
trg_stamp_resolution

When resolved flips to true, the trigger stamps resolved_at/resolved_by itself — the application never sets those columns directly, so a moderation record can't be forged by a compromised client.

Stored procedures & functions

Procedure
sp_register_user(email, handle, password)

Validates the SIIT domain and password policy, generates a random salt, hashes the password, and inserts the new User row.

Procedure · Transaction
sp_submit_content(...)

Inserts the shared Content row (including its optional attachment) and its subtype row (ExamIntel or Materials) inside one BEGIN/COMMIT/ROLLBACK block, so a partial failure never leaves an orphaned supertype row. For materials, also checks that either body_md or file_path is set — the one validation a table CHECK can't express here, since the two columns now live in different tables.

Procedure · Security
sp_moderate_content(content_id, admin_id, remove, note)

Checks the caller's is_admin flag, then soft-deletes (or restores) the target Content row and auto-resolves any open reports against it — centralizing moderation authorization in the database rather than trusting the application layer alone.

Function
fn_course_summary(course_id)

Returns aggregate stats for a course — average difficulty, average time pressure, most-cited topics — computed in SQL instead of pulled client-side, so every screen that needs it stays consistent.
